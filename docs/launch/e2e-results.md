# Phase 10 §10.5 — End-to-End Launch Simulations: Results

**Run date:** 2026-10-12 · **Branch:** `phase-10/hardening` · **Environment:** local, against mocks (not staging)
**Test file:** `apps/backend/tests/integration/launch-simulations.test.ts` (one `describe('launch simulation: …')` per scenario)
**Raw output:** `Phases/evidence/phase-10/launch-simulations.log`

## How these runs work

- **Backend:** the real Fastify app (`buildTestApp`) on real PostgreSQL 17 + Redis 7 (Testcontainers), with a fresh cloned database for the file.
- **Razorpay:** the mock gateway (`integrations/razorpay/mock`). Payments are made with `simulatePayment`, and webhooks are HMAC-signed with the test webhook secret, so the real signature check runs.
- **Shiprocket:** the Shiprocket sandbox on an ephemeral port, called by the **real** production HTTP client (token login, create order, AWB, label, pickup, manifest, cancel). Courier status webhooks go through `POST /api/v1/webhooks/courier-tracking` with the `x-api-key` header.
- **WhatsApp / SMS:** mock providers (Redis outbox). Every send is also written to `notifications_log`.
- **Background jobs:** jobs are recorded with `recordingJobs()`. They are then run through the **real job processors** (`createProcessors`, the same handlers `worker.ts` uses), one run per job id, which matches BullMQ's dedup. The Shiprocket-outage scenario runs **real BullMQ workers** (`startWorkers`) with a 20 ms backoff, so the production retry and dead-letter path is exercised.
- **Fake clock:** `expireHold` backdates `reservation_expires_at` so the expiry sweeper picks the order up. The pickup batch runs with the clock set 3 days ahead.

## Findings

- **Fixed:** a late-payment stockout did not send `order_cancelled` (07 §6). `confirmPayment()` now enqueues `ORDER_CANCELLED` (`notify-order_cancelled-<id>`) after the commit for that branch. Scenario 3 checks both `order_cancelled` and `refund_processed` reach the customer.
